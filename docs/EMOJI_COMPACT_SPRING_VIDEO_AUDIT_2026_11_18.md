## Code-level causes and bounded correction

1. The normal alphabet has an independently measured `strip_container`; Emoji instead re-parents its fixed category tabs into `emoji_grid_shell`. A stale *visible outer strip* consumes a second accessory-height region above the panel. `KeyboardSwitcher.setEmojiKeyboard` hides it, but the prior `EmojiPalettesView.onMeasure` used the strip's instantaneous visibility to reduce the inner panel's height. A transiently restored strip, or a short nominal panel relative to the actual last typing viewport, leaves the compact bottom-aligned Emoji shell below the frame top. Compact `onMeasure` now enforces outer strip `GONE`, then cautiously expands the panel to the last measured **native typing body + genuinely visible outer strip** if and only if the discrepancy is no more than one accessory height and the current window can fit it. This is *reconciliation*, not an unconditional size increase or a Search-height reuse. `KeyboardWrapperView` now rejects reparented Search typing measurements for that native reference.
2. `EmojiPalettesView.revealWithoutFlash` actually faded content from alpha 0 to 1 even while `ValueAnimator` changed the whole Emoji height in every frame. The overlay of a moving GPU blur layer, an opacity fade, and window remeasurement can look like a pulsing/glowing keyboard. Emoji mode children now appear at alpha 1 without a second cross-fade; only deliberate body-height changes animate. The height curve has a bounded critically damped spring-shaped easing over 320 ms, with exact endpoints and no overshoot beyond the IME available height. Android reduced-motion/disabled animation gates and rapid-toggle cancellation remain.
3. `TextKeyData.getDefaultBackground` classified `emoji_search` as a *functional* key unconditionally; therefore Emoji's left Search could not use Enter's action tint. It now receives `BACKGROUND_TYPE_ACTION` **only** in `ELEMENT_EMOJI_BOTTOM_ROW`; Clipboard's Search retains its own original role. Keyboard theme/action-icon rendering handles the accent rather than a hard-coded color.
4. `ViewPager2` previously prepared one adjacent category page and each vertical `RecyclerView` kept the default tiny row cache. Preparing two adjacent pages and reusing four nearby row views per page reduces repeated row inflation/keyboard-view creation during reversing scroll or category swipes. The real moving in-IME RenderNode blur remains active; on-device frame times and memory must be checked before claiming sustained 60/90/120 fps.

## External animation model (for design reasoning, not copied implementation)

- Apple UIKit [`UISpringTimingParameters`](https://developer.apple.com/documentation/uikit/uispringtimingparameters) uses spring force and damping / initial velocity; there is no claim to replicate Apple's private keyboard implementation exactly.
- Android [`SpringAnimation`](https://developer.android.com/reference/androidx/dynamicanimation/animation/SpringAnimation) drives properties with spring stiffness and damping. Here the keyboard's **measured height** must stay bounded by the OS IME viewport, so a monotonic critically damped spring-shaped interpolation is used instead of view translation/overshoot that could reveal the background or intercept touch targets.
