## Measurements and visual acceptance protocol

OPPO's India product page lists Reno10 5G CPH2531, 17.02 cm display, 1080 × 2412 pixels, up to 120 Hz and 240 Hz touch sampling. These are product specifications. Verify owner model, Android release/API, ColorOS build, gesture mode, display/font size, display metrics and actual frame rate. Physical PPI and downscaled 382 px video widths cannot determine dp. [OPPO specifications](https://www.oppo.com/in/smartphones/series-reno/reno10/specs/)

1. Before a layout batch, capture screen and paired rooted view measurements in synthetic Notes, Search, browser URL and numeric fields. Log only app category, build/OS/device/display configuration and geometry. No typed contents. Use `adb shell wm size`, `adb shell wm density`, `adb shell getprop ro.product.model`, `adb shell getprop ro.build.version.release`, `adb shell getprop ro.build.version.sdk`, font scale and runtime navigation insets. With no ADB, record Settings/About and pair owner screenshots with debug-calculated frame bounds.
2. Measure x/y bounds of visible shell, top-edge highlight, strip and accessory, row 1–4 hit and draw boxes, return/search, bottom panel controls, footer glyph centers/bounds, visible nav region, and actual content/visible/touchable top insets. Use same global screen coordinates. Derive dp from `px / (densityDpi / 160)`, compare horizontal and vertical ratios to usable keyboard width, and record Apple screenshot dimensions separately (iOS points and scale are separate).
3. Collect three screen classes: reference-matched dark regular editor, light Search and a true login. Compare dark/light on a neutral background then saturated wallpapers, system 3-button nav, orientation, and split/one-handed profiles. For iPad, collect a comparably labeled reference or expressly leave it pending. Historical media compression and cropping disqualify absolute color/size picks.
4. Proposed initial sweep, subject to Reno10 capture: 30–36dp strip, ~18–22dp secondary glyph size, ~14–18dp ordinary legible labels depending on key baseline, 48dp independent primary footer hit regions, 0.75–1.25dp optically thin highlight, 3–6dp inter-key visual gaps where screen width permits, 7–8 Emoji columns across compact portrait. Preserve key hit coverage while changing visual gaps. Read actual current config before tuning. Treat radius and exact height as measured decisions, not Apple numeric claims.
5. Working acceptance targets: stable same-mode shell top/footer within ±1dp after layout across regular/symbol/numeric/Emoji/Clipboard/Toolbar in one editor and config. Accessory appear/disappear should avoid repeated window measurement, with an explicitly deliberate one-time size transition if collapsing the otherwise-empty strip. Three visually balanced slots over the key body, utility control never appears as a fourth suggestion. Across one-handed/landscape deliberate differences are allowed. Verify TalkBack node bounds, 2× font scale and fallback when translated labels truncate.

## Geometry, material and interaction architecture

- **Single geometry owner.** Work within InputView, RoundedKeyboardFrameView, KeyboardSwitcher and existing resource-qualified config. Make measured shell height equal to panel body + shared accessory allocation + footer + actual nav inset, counted once. Resolve height based on active editor/config once, then give available panel body bounds rather than deriving independent Emoji/Clipboard heights. Preserve Resize, one-handed and landscape hooks. Current portrait resources include 205.6dp base model height, 36dp strip/edge width, 48dp footer, 10dp optical bottom inset/compensation, 52.8dp popup key height and 12.5% Emoji column width. Exact window height includes model scaling, margins, panel and display constraints.
- **Insets and dismissal.** Visible nav inset from RoundedKeyboardFrameView is after footer. Observe real inset in gesture navigation even if the system pill is hidden; do not add a fixed placeholder. Compare glyph top to preceding row bottom and glyph bottom to usable lower edge, excluding actual system gesture/nav area where appropriate. InputView intercepts a downward strip pull, sends ACTION_CANCEL to children, and calls the IME once on half-height pull or measured fling. Verify downward threshold, upward alternatives, horizontal toolbar/chip drag, touch exploration, multi-touch, hardware Back, rapid reopen and scroll safety. Let Android/ColorOS animate actual hide. Audit FrostedGlassHelper's delayed native blur cleanup and rapid reopen rejection before changing timing. [Android IME insets](https://developer.android.com/reference/android/inputmethodservice/InputMethodService#onComputeInsets(android.inputmethodservice.InputMethodService.Insets))
- **Existing frosted path.** Reuse KeyboardTheme/Colors → FrostedGlassHelper → RoundedKeyboardFrameView. Keep neutral light/dark shell and a slim top specular highlight. Use the platform's cross-window blur where supported and opaque-enough tonal fallback when disabled; RenderEffect filters local view content, including content people need legible. Probe actual ColorOS behavior in an external host and compare blur on/off with app content. Cache paths/paints/radii per layout/theme. Preserve OS-level clipping, forced contrast and secure windows. No pixel capture, private vendor hacks or extra renderer are needed for this plan. [Android window blurs](https://source.android.com/docs/core/display/window-blurs)
- **Accent contract.** Preserve automatic OG Frosted Glass light/dark and the existing appearance simplification. Expose existing off plus manual curated swatches and optional automatic restrained palette from system_accent1_500 on Android 12+. Use CIELAB selection already present; near-neutral accents can fall back to a known blue, and resolved foreground is chosen from measured contrast. Audit all role consumers: KeyboardTheme's functionalBase/specialBgBase can use appleActionAccent, beyond a single action key, and Emoji category highlight already maps the palette. Product default should tint context-specific emphasized actions (e.g. Search) and deliberate selection affordances; shell/background, ordinary keycaps, Clipboard and unrelated modifiers stay neutral absent a scoped user setting. Preserve custom historical frosted controls and migrate only distinct old defaults when warranted. Avoid adding old iOS Clear/Tinted presets as duplicate global selectors.
- **Glyph inventory.** Audit glyph source and position for Shift off/on/locked, Backspace, 123/ABC, symbol layer, number layout, comma/period, context @/#, locale ₹, globe, Emoji, microphone inactive/listening/stopping, Search, Return, Go, Next, Done, Send, Clipboard/pin/clear/dismiss/undo, toolbar/accessory, and category/search. Confirm baseline and mirrored Back/Forward where appropriate. Reuse original project vectors or rights-cleared assets; Apple SF fonts/Symbol/Emoji downloads require separate redistribution review. Verify tab category action labels and rendered cap spacing in both themes. Caption is one subdued mark at intended space-area edge, outside the hit logic. Preserve correction and input-action labels in accessibility even when using icons.
- **Suggestion strip.** SuggestionStripLayoutHelper installs a compound drawable at L554 for more-suggestions. Remove its visual use while preserving hold/upward reveal and accessibility action in SuggestionStripView. Keep accepted/typed/alternate indices, case, autocorrect metadata, long-word ellipsis inside text and overflow reachable. Put a compact independent trailing utility in a measured rail or compensate optical centering with flexible slots. Test ordinary 0, 1, 2 or 3 words, long URLs, corrections, Emoji pairs, app completions, autofill and empty/accessory-only states. Never reserve a second empty toolbar row.
- **Footer and shortcut events.** Existing source uses a 160×86dp popup and 48dp square targets at fixed offsets, with alpha 242/255 on circles. Replace the redundant Emoji target with Toolbar while retaining tap-to-Emoji and tap-to-ABC return. Treat the footer as an overlay on its originating panel. Fit a shallow arc or joined translucent popup to actual measured edges; clamp center and geometry together and align visual and hit positions in raw screen coordinates. Six state boundaries: down, held, hover/select, release, cancel, editor change. Give haptic on open and optionally only when entering a distinct target. From main and Emoji, direct action dispatch: Clipboard starts history if enabled and works from Emoji; Toolbar enters its accessible panel explicitly; Settings opens once on a deliberate selection. Do not route the arc through a generic full-screen toggle that rejects Emoji, and do not invoke unconditional panel toggle to dismiss the IME. Preserve shortcuts' TalkBack custom actions, normal mic tap and IME-switch hold. Maintain left/right layout or defined RTL mirroring with matching spoken order.
- **ABC and Emoji navigation.** Keep one letters route, preferably footer ABC, with shared icon/description and preserved Delete/Space behavior where applicable. The bottom-row ABC sources are `app/src/main/assets/layouts/emoji_bottom/emoji_bottom_row*.json`; verify both action variants, custom bottom rows/search, Clipboard and number before removing any entry. Category tap may scroll directly to first category item. Free-scroll within one category must stop mid-grid. Replace whole-page paging with a horizontal, recycled column/grid layout keyed by category; each column stores three rows or density-dependent pairs. Swiping stays continuous and only optionally settles near current/next category boundary on qualifying low-speed release. Alternative: no fling helper and explicit category tab selection, then introduce boundary assist only if testing shows benefit. Keep PopupKeys tones, grapheme commits, category tab sync, search/results, region-aware recents and persistent Emoji row independent. No inter-category feedback loop from scroll listener/programmatic scroll.
