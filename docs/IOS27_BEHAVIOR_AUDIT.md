# brrBoard behavior audit and conflict priorities

## Scope and evidence

The audit compares the current v1.0.16 source with the supplied iOS keyboard screenshots and Apple's iPhone guidance. It records implementation intent separately from verified phone behavior. Android `EditorInfo`, field privacy, and installed speech services remain authoritative where iOS behavior does not map to Android.

- Apple guidance: [onscreen typing and keyboard settings](https://support.apple.com/guide/iphone/type-with-the-onscreen-keyboard-iph3c50f96e/27/ios/27), [predictive text](https://support.apple.com/en-asia/guide/iphone/iphd4ea90231/27/ios/27), [dictation](https://support.apple.com/guide/iphone/dictate-text-iph2c0651d2/27/ios/27), [keyboard switching](https://support.apple.com/guide/iphone/add-or-change-keyboards-iph73b71eb/27/ios/27), and [emoji](https://support.apple.com/en-gb/guide/iphone/iph69df21ec5/27/ios/27).
- Owner recordings: 116.8-second `VID_20261115_115114(2).mp4` and 25.7-second `VID_20261114_230053.mp4`. They remain private. The longer capture was reviewed at one-second intervals and the keyboard-state transitions were rechecked at their change points. This is not a claim that each of its 3,503 frames was individually inspected. The short capture visibly includes Android's offline speech-model prompt and an IME picker. Narration was not reliably transcribed.
- In the longer clip, the displayed phrase and suggested candidates do not always look related. That shows a relevance problem worth testing; it does not identify the prediction engine's cause. The microphone animation/UI appears, but audio capture, offline processing and committed text are not proven. The keyboard changes through Symbols, the enlarged number pad, Emoji and Clipboard. The clip predates the current draft, so it does not validate these edits.
- The 0 B data-use screen in earlier footage is one observation. Verify the manifest/permissions in the signed artifact and test recognition with airplane mode; do not treat the screen as proof of offline behavior.

## Conflict decisions for the current patch

1. **Long-press 123 outranks popup metadata.** Capture `isAlphabetKeyboard()` at touch-down before `onPressAlphaSymbol` changes the layout; resolve this hold in `PointerTracker.onLongPressed` before generic popup handling. The saved start state, rather than the current post-press keyboard, decides whether this is the enlarged-numpad gesture.
2. **Tap wins when the long-press timer does not fire.** A normal tap completes the existing Symbols transition. Movement off alphabetic 123 cancels the hold timer and disables slide-to-popup selection for that gesture, avoiding accidental punctuation.
3. **Emoji arc is the only touch-menu implementation.** Keep tap-to-Emoji and the owner-confirmed hold/drag/release targets. Do not layer a platform `PopupMenu` over the same touch listener.
4. **OS owns hide animation.** The app recognizes an intentional strip drag, then requests IME dismissal once. There is no app-owned offset or blur state to restore. This reduces competing animation paths, but only the Reno10 can establish whether ColorOS removes the reported flash.
5. **EditorInfo outranks screenshot imitation.** Field-specific actions/layouts follow the host application's advertised input/action flags. Screenshot key positions do not justify overriding a search, URL, email, numeric or password field.
6. **Privacy and identity outrank appearance changes.** Keep package, signer, update continuity, protected-field guards and the no-network permission check intact. A visual parity change must not weaken these.

## Remaining differences and acceptance

Apple documents QuickPath, inline prediction, rich context-aware suggestions, on-device dictation in many languages, and a keyboard-switch hold menu. brrBoard approximates only the native/offline-safe subset available to an Android IME. It does not claim Apple's prediction model, inline completion/reversal, dictation editing commands, universal image/file paste support, two-finger trackpad selection, exact proprietary rendering, or concept-art measurements. The user's 123-hold numpad and three-way globe arc are intentional Android customizations.

After the signed build is installed on the Oppo Reno10 5G, check in this order:

1. Tap and hold alphabetic 123 (including just below the long-press timeout), tap 123, and slide off it. Confirm exactly one expected layout/result each time. Verify the enlarged pad's return and footer.
2. Swipe from the left, center and right of the suggestion strip: short release, long drag and fast flick. Then test suggestion/A-button taps and verify one OS dismissal without the background blur flash.
3. Compare outer bounds and bottom alignment in typing, Emoji, Clipboard and enlarged numpad, with gesture navigation and three-button navigation. Count visible emoji columns at default display/font scale and check touch target feel.
4. Test English and Hinglish phrase relevance with the same text in a search field and a normal editor. Try copied text, image and file in apps that accept each MIME type. Keep screenshots private if they expose user text.
5. Test dictation in airplane mode for English, Hindi and Romanized Hinglish: permission/model prompts, start, stop, cancel, active-field changes, duplicate results and insertion. Record Android/ColorOS version, recognizer provider, locale and visible error only—not typed content.
6. Compare OG Frosted Glass, OG Frost Tinted, iOS Clear and iOS Tinted. Confirm tint affects only the intended controls; verify brightness, contrast, curved screen edges, key hit areas, symbols, phone/URL/email/Search actions, orientation and in-place update.

Previous independent debug workflows failed 14 of 180 tests. That history is not a green test result and does not establish whether this source patch changes those failures. The owner requested an APK; compile/package/sign/release checks are run for it, but do not claim hardware behavior without the owner's report.
