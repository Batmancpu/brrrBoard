## Authoritative sources and workflows

- `docs/releases/notes.json` is the **human-authored changelog for the NEXT signed application update**. Update it **with every app-changing commit**. Describe every user-facing addition, repair, behavior/privacy change, and relevant limitation; no empty generic filler. If several source commits accumulate before a signed release, make this file the cumulative delta since the last successfully published signed release. Do **not** invent a version number or publication timestamp here.
- `.github/workflows/brrrboard-build-debug.yml` blocks a `main` application change unless that same commit also updates `docs/releases/notes.json`. It tests the generator and verifies a bundled history asset. Debug-only versions are not inserted into the user-facing signed-release list.
- `.github/workflows/obtainium-release.yml` determines the real `1.0.${GITHUB_RUN_NUMBER}` from the **original** Obtainium workflow, reads existing signed GitHub release tags and their structured notes, and generates `app/src/main/assets/version_history.json` just before compiling. It verifies that the APK actually contains the matching current version. It publishes the same human changes and machine-readable marker in the GitHub release body for future runs.
- `tools/generate_version_history.py` is deterministic and dependency-free. Run `python3 -m unittest discover -s tools -p 'test_generate_version_history.py' -v` locally before submitting. It ignores debug/prerelease/unverified records; **do not scrape arbitrary commits and present them as published changes**.
- `docs/releases/legacy_verified.json` contains only two source-inspected releases without historical structured notes: `v1.0.183` and `v1.0.186`, with actual GitHub `published_at` and exact commit IDs confirmed on 2026-11-20. Do not backfill older releases without reliable, individually verified descriptions.
- `app/src/main/assets/version_history.json` is a checked-in fallback for local/development builds. The release workflow regenerates it with exact signed version numbers and available prior history; do not treat the fallback as the release source of truth.

### Date/time accuracy

For previously published signed versions, the app shows GitHub's actual UTC `published_at`, converted to the phone's time zone and labeled **Published on GitHub**. A release being packaged cannot contain its own future GitHub publication timestamp, so the newest build embeds the UTC time at which the signed-release build was prepared and labels it **Release build started**. On the next release, that record is replaced by its exact GitHub publication time. **Never mislabel the preparation timestamp as the actual publication time.** No live GitHub API call occurs on the phone and the keyboard retains zero network permissions.
