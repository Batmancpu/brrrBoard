| Surface | Current route and limits | Future action |
| --- | --- | --- |

### Source-backed risks and data contract

- **Cross-panel route.** BoardFooterView releases selected KeyCode.CLIPBOARD via LatinIME.onCodeInput. InputLogic L840 branches: history enabled lets KeyboardState.onEvent switch; disabled immediately calls clipboard paste. KeyboardState L694 invokes setClipboardKeyboard if enabled; Switcher L1160 hides Emoji and tabs without the stop visible in its alphabet path. The separate Switcher ACCESS_POINT guard L1447 blocks whole-panel access from Emoji/Clipboard. The observed arc at 23 s proves it can appear. Test whether release hit target, enabled preference, old editor/view state or handler order causes lost selection. Direct panel navigation should avoid immediate paste for a control labeled Clipboard when history is unavailable. Preserve the existing explicit Paste action and user settings. Confirm keyboard can return to letters/search or the originating panel as designed without committing content or hiding the IME.
- **Sensitive data mismatch.** `recentTextClip` and `recentRichPaste` already check sensitive ClipDescription, input type, password variants, no-personalized-learning and age. `fetchPrimaryClip` L488 captures history and copies first text/image without the same sensitive-flag gate. Screenshot observer L87 checks preferences and scoped permissions; decide explicit privacy behavior for when the editor is incognito. Treat this as a code-path finding pending a synthetic sensitive-clip regression test, not an observation of owner data exposure. Ensure active sensitive clip never appears or persists in new history. Confirm explicit privacy rules for already-pinned entries and disable history panel in secure editors unless the owner independently requests safe manual access.
- **Dismissal state.** markClipDismissed persists raw copied text or image URI plus timestamp in preferences. For future design use in-memory clip identity/opaque bounded identifier and clear stale matching data. Preserve dismiss of current item across same-editor layout refresh, allow newly copied identical content to resurface as policy permits, and migrate removal of obsolete raw preference keys without deleting unrelated pinned history. Never include clipboard text, image, raw URI or screenshot filenames with identifying data in logs. Screen set from screenshots can contain credentials; retain only scoped grants and explicit opt-in.
- **Rich-image return ambiguity.** ClipboardHistoryView.onKeyUp L397 calls `pasteHistoryEntry`, which returns false for both a plain text entry and a failed image commit. Current else falls back to `onTextInput(clipContent.text)` in both cases. Review ClipboardImageHistoryClip encoding and ensure refusal of image never inserts a serialization marker/URI in text; use an explicit type or outcome (plain, committed, rejected). Check MIME advertisement with EditorInfoCompat, commit once with InputConnectionCompat, control lifecycle of app-granted URI permission, and verify error UX when editor rejects or file vanishes. `LatinIME.commitKlipyContent` is the currently functional generic path despite the legacy name. Preserve same method callers while extracting shared MIME/success contract if necessary. [Android image keyboard support](https://developer.android.com/develop/ui/views/touch-and-input/image-keyboard)
- **Duration and files.** ClipboardDao.clearOldClips skips active listener, retains pins, expires eligible nonpinned entries under setting; cached image cleanup runs on expiry/clear. Audit dismiss/undo lifetimes and atomic cache path, bound file size/thumbnail decode, and reject unsupported URI schemes. Permission revoke and unavailable MediaStore/SAF reads should degrade safely without retry storm. Staff tests use synthetic text, link and small image assets. Delete/cancel must avoid leaks while allowing undo to temporarily retain its own entry. Verify legacy persisted images still open.
- **Design.** clipboard_history_view.xml has 38dp circular action buttons, bold 20sp heading, body wrapping, separate capped panel height math and bottom typing row. Use shared measured shell. Header remains accessible with a modest ~14–16sp title, neutral role icons with full target sizes, quiet controls separated from scroll region. Rounded image clip and properly cropped thumbnail display, 2-line text, type-aware link labels, pin state, empty state and undo all fit. Keep clear semantics unambiguous, preserving current pin/clear behavior. Use cached/no-allocation gradient overlay in scroll viewport only when it can scroll, with end gutters so first/last items and undo remain fully reachable. A local alpha mask is optional if visible banding warrants it. Full-list blur or repeated offscreen layers obscure text and threaten GPU budget.
- **Chip.** Current chip uses max-40-character text or generic image/file label, and explicitly hides its preview ImageView. Build neutral slim chip with 20–24dp image preview only when editor accepts MIME and eligible image metadata is safe; keep X and paste separate, stable compact height, one-line truncation, accessibility names and async thumbnail bound to current clip/editor. Use no direct host UI cloning. Exercise text paste, rich image, unsupported editor, rejected MIME, expired URI, permission revoke, X, repeat copy, focus change, screen hide, and accessibility double-tap. Keep text-only fallback explicit.

## Inline autofill — preserve the provider

Android 11+ IME support is advertised in method.xml. LatinIME.onCreateInlineSuggestionsRequest/onInlineSuggestionsResponse goes through InlineAutofillUtils. Existing minimum/maximum widths are hard-coded 100/740 px, height uses suggestion strip dimen, three presentation specs support some managers, max six responses. AndroidX style negotiates background, title, subtitle and icon dimensions; provider supplies actual content and action. Inflation runs asynchronously, child order can vary, and InlineContentClipView does SurfaceView clipping in a draw listener. Keep this clipping invariant when restyling. Owner reports Proton Pass inline autofill works; v1.0.57 version/device acceptance has not been established. [Android inline autofill contract](https://developer.android.com/identity/autofill/ime-autofill) · [Proton Pass Android](https://proton.me/support/use-pass-android)

1. Build size bounds from current strip width and density, populate supported style versions, preserve three specs and multi-chip scroll until benchmarks/provider tests support changing them. Refine roles with compact px/dp conversion, contrast and native-provider compatibility. Asynchronous inflation may be rejected or return null; render only attached current generation and maintain provider order.
2. Keep provider chip in an IME-owned compact container with an optional dismiss affordance. Do not classify or reconstruct provider data, parse text, screenshot content, or alter actions. Separate styling of provider-owned surfaces from IME clipboard view. Provider icon may remain provider-specific.
3. Define accessory arbitration in LatinIME/strip. For current eligible login editor, active provider autofill has priority over other IME chips; focus-generation change removes it. For ordinary text, a fresh valid user clipboard chip can occupy accessory until dismissed or typing should resume. Provider/no-provider menu fallback is Android-owned, no custom credential retrieval. Manual toolbar selection should be explicit and reversible; do not enqueue stale clipboard/dictionary updates over a provider response. Shared slot retains measured height contract.
4. Verify Proton dummy credentials in browser and a native form, text vs password fields, 2FA/pinned if offered, multiple suggestions, dismiss, focus/keyboard changes, dark/light, patched size at multiple densities, provider unsupported fallback and TalkBack. Synthetic credentials only. Accept provider callback via normal platform path. Ensure no Clipboard/Emoji personalization or dictation appears in restricted fields.

## Voice — exact path, provider contract and acceptance

- Owner’s issue [DictateKeyboard #359](https://github.com/DevEmperor/DictateKeyboard/issues/359) is the matching discussion. The maintainer distinguishes RecognitionService (inline), an activity (takes UI) and a voice IME (switches keyboards); caller chooses mechanism. Owner wants Dictate only, inline, English-only, and uses their configured provider/API. Latest upstream release observed v6.4.0; verify the owner’s installed Dictate version separately. [Dictate release](https://github.com/DevEmperor/DictateKeyboard/releases/tag/v6.4.0)
- **Tap-to-settings path verified in source:** BoardFooterView bind L79 → VOICE_INPUT → LatinIME.onEvent L1926 → InlineDictation.toggle/start → selectedDictateRecognitionService (L240+). It reads Android Secure voice_recognition_service, requires package net.devemperor.dictate, then verifies recognition-service component/class from package-manager query. If null, start L56–61 shows setup toast and unconditionally calls openVoiceInputSettings L270; ACTION_VOICE_INPUT_SETTINGS is routed by Android/OEM. This is a directly reachable explanation for Digital Assistant/voice-input settings. Distinguish absent secure setting, different provider, component mismatch, invisible/unavailable service, and Android/OEM policy with reason-coded diagnostics only. Exact failing reason on this phone is unproven.
- **Hold is a separate path:** BoardFooterView timer → LatinIME.switchBoardInputMethod → ImeCompat system switch or picker. Keep hold distinct, measure accidental hold threshold and verify touch cancel/new pointer/gesture did not invoke tap. On tap normal failure should give a brief footer state/actionable hint, with voice settings only via explicit separate Settings action. No fallback recognition engine, default generic cloud recognizer, manual keyboard change or Dictate activity on a normal tap. Verify manifest visibility and permission before binding. Do not write Settings.Secure or use accessibility/hidden settings APIs. [Android SpeechRecognizer](https://developer.android.com/reference/android/speech/SpeechRecognizer)
- **Language is provider-owned:** brrBoard requests locale matching English subtype or en-IN, up to three alternatives, and API-34+ language detection. On final result, rejects non-English language metadata and Devanagari and accepts first remaining candidate if same InputConnection. Absence of language metadata and Romanized Hindi are unresolved. Dictate’s upstream RecognitionService starts RecognitionSession/DictateController using its active language preferences and returns result string, examined at 7f0dd8b4f28e0cb3ab82d48f946a008989c5c2e8. Verify owner exact version (recent source may differ). Set Active language to English and Follow keyboard language off in Dictate. Test purchased provider with synthetic utterances; provider English failure persists upstream even if brrBoard rejects it. Do not claim English is guaranteed by a recognizer hint. For untagged text, reject clearly non-English script, use conservative high-confidence rejection only if validated, and avoid applying text-typing Hinglish heuristics to voice. If provider still emits Romanized non-English in English mode and lacks reliable locale signaling, handoff to Dictate issue with redacted version/errors or offer explicitly explained safe suppress-unverified trade-off. [Upstream source](https://github.com/DevEmperor/DictateKeyboard/commit/7f0dd8b4f28e0cb3ab82d48f946a008989c5c2e8) · [RecognizerIntent](https://developer.android.com/reference/android/speech/RecognizerIntent)
- **Session state:** Idle → starting → listening → stopping/processing → final, failure, timeout or cancel → idle. Existing SpeechRecognizer identity, deadline, footer, connection check and cancellation on start/finish/hidden are reusable. No partial text currently inserted (onPartialResults ignores it); keep stable final-only insertion as baseline. Revalidate visible editor/connection/generation and input policy before final; discard late callbacks after switch, rotate, lock, dismiss or another session. Microphone alone indicates listen/process; provide accessible stop/cancel roles and exact-once final via onTextInput. Permission denied, missing service, airplane mode, provider unavailable, empty/no speech, rejected language and device-specific settings should never create pending content. Voice privacy guard from a6558820 is active because SettingsValues.mShowsVoiceInputKey excludes incognito. Maintain password/visible password/no-personalized constraints too. Keep Dictate API credentials and raw audio/transcripts out of brrBoard.
- **Device pass:** Record brrBoard SHA/version, Dictate version/provider label without account, Android/ColorOS/API, selected service class and language flags. From external Notes: short tap starts Dictate inside keyboard; explicit stop yields exactly one English insertion and idle glyph; repeat rapidly; switch to another field while waiting; hide/popup/back; test restricted fields; switch OS provider or deny permission and ensure no settings launch or fallback. In Hinglish typing subtype voice still produces English. Try 10 short English phrases, 5 proper-name/punctuation prompts and 5 deliberately non-English/ambiguous source utterances using test text only. Android-level proof of identity and English acceptance are separate. Historical guards shipped v1.0.26/1.0.44, English result policy around v1.0.38, explicit bind v1.0.50. None alone closes the newest symptom.
